# MANDATORY REQUIREMENTS — CRUD & VALIDATION

These requirements are NON-NEGOTIABLE and MUST be fully implemented.

## 1. COMPLETE CRUD OPERATIONS

Every major entity must support complete CRUD functionality.

### Student CRUD

Implement:

* Create Student
* Read/Get All Students
* Read/Get Student by ID
* Update Student
* Delete Student

REST endpoints:

POST   /api/students
GET    /api/students
GET    /api/students/{id}
PUT    /api/students/{id}
DELETE /api/students/{id}

The frontend must provide working UI for all five operations.

The Student Management page must allow the user to:

* View students
* Search students
* Filter students
* Open student details
* Add a student
* Edit a student
* Delete a student
* Confirm before deletion
* Display success/error messages

DO NOT use mock data after API integration.

# 5. MANDATORY VALIDATION

Validation MUST exist on BOTH:

### Frontend

and

### Backend

Frontend validation provides immediate user feedback.

Backend validation is the final authority and MUST NOT be bypassable.

Never rely only on frontend validation.

---

# 6. STUDENT VALIDATION

Validate every student field appropriately.

### Student ID

Rules:

* Required
* Cannot be blank
* Must be unique
* Should follow a reasonable format

Example:

JCET001

If a duplicate Student ID is submitted:

Return:

HTTP 409 CONFLICT

Message:

"Student ID already exists."

---

### First Name

Rules:

* Required
* Cannot be blank
* Minimum 2 characters
* Maximum 50 characters
* Should contain valid name characters

---

### Last Name

Rules:

* Required
* Cannot be blank
* Minimum 1 character
* Maximum 50 characters

---

### Email

Rules:

* Required
* Must be valid email format
* Must be unique

Example:

[student@example.com](mailto:student@example.com)

Invalid:

student@
student.com@
abc

---

### Phone

Rules:

* Required
* Must contain a valid number of digits
* Validate Indian mobile number format where appropriate
* Do not accept arbitrary alphabetic characters

---

### Date of Birth

Rules:

* Required
* Must be a valid date
* Cannot be in the future

---

### Gender

Rules:

* Required
* Must be one of the supported values

Example:

MALE
FEMALE
OTHER

---

### Department

Rules:

* Required
* Must reference an existing department

Do not allow a student to reference a department that does not exist.

---

### Course

Rules:

* Required
* Must reference an existing course

Ensure the selected course belongs to the selected department.

---

### Semester

Rules:

* Required
* Must be a valid semester number
* Reject invalid/negative values

---

### Admission Year

Rules:

* Required
* Must be a valid year
* Must not be in an impossible/future range

---

### Status

Allowed values:

ACTIVE
INACTIVE
GRADUATED

Reject unsupported values.

---

# 10. FRONTEND VALIDATION UX

Every form must show clear validation messages.

Example:

Student ID
[________________]

"Student ID is required."

Email
[student@]

"Please enter a valid email address."

Phone
[123]

"Please enter a valid phone number."

Do NOT show vague messages such as:

"Invalid input."

Tell the user exactly what needs to be corrected.

---

# 11. BACKEND VALIDATION

Use Jakarta Bean Validation:

@NotBlank
@NotNull
@Email
@Size
@Pattern
@Min
@Max
@Past
@PastOrPresent

Use appropriate annotations based on the field.

Example:

@NotBlank(message = "Student ID is required")
private String studentId;

@Email(message = "Please provide a valid email address")
@NotBlank(message = "Email is required")
private String email;

Do NOT put validation only on JPA entities.

Prefer validating request DTOs.

---

# 12. UNIQUE CONSTRAINTS

Enforce important uniqueness at BOTH:

Application level

AND

Database level.

At minimum:

students.student_id → UNIQUE

students.email → UNIQUE

departments.code → UNIQUE

departments.name → UNIQUE

courses.code → UNIQUE

Handle duplicate database constraint violations gracefully.

Do not expose raw SQL/database error messages to the frontend.

---

# 13. ERROR RESPONSE

All validation errors must return structured responses.

Example:

{
"success": false,
"message": "Validation failed",
"errors": {
"studentId": "Student ID is required",
"email": "Please provide a valid email address",
"phone": "Please provide a valid phone number"
}
}

For duplicate resources:

{
"success": false,
"message": "Student ID already exists"
}

For missing resources:

{
"success": false,
"message": "Student not found"
}

---

# 14. HTTP STATUS CODES

Use proper HTTP status codes.

201 CREATED
→ Successful creation

200 OK
→ Successful read/update

204 NO CONTENT
→ Successful deletion where appropriate

400 BAD REQUEST
→ Invalid request/validation failure

401 UNAUTHORIZED
→ User is not authenticated

403 FORBIDDEN
→ User does not have permission

404 NOT FOUND
→ Resource does not exist

409 CONFLICT
→ Duplicate resource/unique constraint violation

500 INTERNAL SERVER ERROR
→ Unexpected server error

Do NOT return HTTP 200 for every situation.
